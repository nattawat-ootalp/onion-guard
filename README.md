# OnionGuard — ระบบ AI คัดกรองเชื้อราบนหอมแดงด้วยแสง UV 365 นาโนเมตร

คัดกรอง "ความผิดปกติที่สัมพันธ์กับเชื้อรา" บนหอมแดง จากภาพถ่ายใต้แสง UV 365nm
ด้วยการสกัดฟีเจอร์ + Gradient Boosting แล้วแสดงผลบนเว็บ

> **สถานะ: ใช้ข้อมูลจริงแล้ว** — โมเดลปัจจุบันเทรนจากหอมแดงจริง 60 หัว
> (พบ 35 / ไม่พบ 25) ป้ายกำกับจาก CompactDry YM ทุกหัว
> ตัวเลขด้านล่างเป็นค่าประมาณจากกลุ่มตัวอย่างขนาดเล็ก ช่วงความเชื่อมั่นกว้าง

## ผลปัจจุบัน

วัดด้วย 5-fold cross-validation × 20 shuffle บน seed ที่ไม่เคยใช้ตอนเลือกวิธี
(`reports/experiments/verify_finalists.csv`)

| | ค่า | เกณฑ์ | ผล |
|---|---|---|---|
| Accuracy | 0.816 | ≥ 0.80 | ผ่าน |
| Recall | 0.846 | ≥ 0.80 | ผ่าน |
| Kappa | 0.620 | ≥ 0.61 | ผ่าน |
| Specificity | 0.774 | — | |
| AUC | 0.905 | — | |

**อ่านตัวเลขนี้อย่างระวัง** — bootstrap สุ่มหัวหอมใหม่ 4000 ครั้งได้ช่วง
kappa 0.49–0.86 แปลว่าถ้าเก็บหอมชุดใหม่ 60 หัว มีโอกาสราว 78% ที่จะผ่านเกณฑ์
ช่วงกว้างขนาดนี้มาจาก n=60 ล้วน ๆ ไม่ใช่จากตัวโมเดล

`src/train.py` รายงาน kappa 0.544 เพราะใช้ shuffle เดียวตามวิธีในเล่ม
ที่ 12 หัวต่อ fold ตัวเลขจาก shuffle เดียวแกว่งมาก ค่าที่ควรอ้างคือ 0.620

## การทำงาน

ถ่ายด้วยมือถือ (Pro mode ล็อก ISO/shutter/WB) → อัปโหลดผ่านเว็บ → เซิร์ฟเวอร์ประมวลผล
มือถือไม่ได้คำนวณอะไร เพราะโมเดลเป็น Python รันในเบราว์เซอร์ไม่ได้

```
อัปโหลด (JPEG / DNG)
  → Pillow/rawpy    อ่านไฟล์ + หมุนตาม EXIF
  → onion_detect    หาหัวหอม แล้วครอบ+ย่อให้อยู่กลางกรอบขนาดคงที่
  → predict         สกัดฟีเจอร์ 24 ตัว แล้วเลือกใช้ 10 ตัว
  → GradientBoosting ตัดสิน + วาดวงทับจุดที่เจอ
```

**ทำไมต้องครอบใหม่ทุกภาพ:** threshold ขนาด blob เป็นจำนวนพิกเซลตายตัว
ถ้าถ่ายใกล้/ไกลต่างกัน "จุดเล็ก" กับ "ปื้นใหญ่" จะหมายถึงคนละขนาดจริง
วัดจากภาพจริงสองใบ ตำแหน่งต่างกัน 28% ขนาดต่างกัน 14%

**ภาพแสงปกติ:** ถ่ายหัวเดิมซ้ำใต้ไฟห้อง ใช้แยกจุดที่เรืองแสงเฉพาะใต้ UV
ออกจากคราบที่เห็นได้ในแสงธรรมดา ตรวจหาหัวหอมด้วยแกนสี a\* ของ CIELAB
ไม่ใช่ความสว่าง เพราะพื้นหลังกระดาษสาสว่างพอ ๆ กับหัวหอม (เดิมใช้ความสว่าง
แล้วพลาด 32/60 หัว)

## กระเทียม: ตรวจแบบ “เทียบกับของปกติ”

หอมแดงใช้ตัวจำแนกสองคลาส เพราะทุกหัวในชุดฝึกมีผลเพาะเชื้อกำกับ
กระเทียม **ไม่มีหัวไหนเลยที่มีผลแล็บ** — ที่ถ่ายไว้ทั้งหมดคือกลีบที่ดูปกติ
ซึ่งเป็นข้อมูลคลาสเดียว เทรนตัวจำแนกสองคลาสไม่ได้

จึงเปลี่ยนวิธี: เรียน **“รูปร่างของความปกติ”** จากกลีบปกติเหล่านั้น
(มัธยฐาน + MAD ของแต่ละฟีเจอร์) แล้ววัดว่ากลีบใหม่ห่างจากช่วงนั้นกี่เท่า

```
score = max ของระยะห่าง (z) ทุกฟีเจอร์
        z ≥ เกณฑ์  →  "พบความผิดปกติที่สัมพันธ์กับเชื้อรา"
        z <  เกณฑ์  →  "ไม่พบความผิดปกติ"
```

- **ใช้ max ไม่ใช่ผลรวม** — ฟีเจอร์เดียวที่หลุดช่วงปกติไปไกลคือตัวคำตอบ
  ถ้ารวมกัน ฟีเจอร์ที่เพี้ยนนิดหน่อยสิบกว่าตัวจะกลบตัวที่ผิดจริงได้
  และการใช้ max ทำให้บอกได้ว่า **ฟีเจอร์ไหนคือเหตุผล** ซึ่งรายงานกลับไปให้ผู้ใช้ด้วย
- **ใช้มัธยฐาน/MAD ไม่ใช่ค่าเฉลี่ย/SD** — ชุดข้อมูลเล็กและยังไม่ได้ตรวจทีละใบ
  ภาพที่ครอบพลาดใบเดียวก็ดึงค่าเฉลี่ยและถ่าง SD จนกลืนความผิดปกติจริงได้
- **เกณฑ์คิดจากกลีบปกติเอง** (เปอร์เซ็นไทล์ 97.5 ของคะแนนตัวเอง × margin)
  จึงแปลว่า “ห่างจากปกติมากกว่าที่กลีบปกติเคยห่าง” ไม่ใช่เลขที่ตั้งขึ้นลอย ๆ
- **ทิศทางสำคัญ** — จุดเรืองแสง/ปื้น นับเฉพาะที่ “มากกว่า” ปกติ
  (จุดน้อยกว่าปกติคือกลีบสะอาดกว่า ไม่ใช่กลีบแปลก) ส่วนสี/ความสว่าง/พื้นผิว
  ผิดไปทางไหนก็ถือว่าแปลก

**คำที่ใช้จงใจให้เท่ากับสิ่งที่ทำได้จริง** — ระบบยังไม่เคยเห็นกลีบที่ยืนยันว่าพบเชื้อ
แม้แต่กลีบเดียว จึงพูดได้แค่ “ผิดปกติจากกลีบปกติ” ไม่ใช่การระบุว่าเป็นเชื้ออะไร
(เป็นถ้อยคำเดียวกับฝั่งหอมแดงที่รายงานใช้อยู่แล้ว)

```
python src/train_garlic_anomaly.py        # → models/garlic_anomaly.json
```

ถ้ายังไม่มีไฟล์นี้ เว็บจะสร้างค่าอ้างอิงเองจากกลีบปกติที่มีในฐานข้อมูล (แคชไว้ 15 นาที)
โดยนับเฉพาะแถวที่ **ยังไม่เคยถูกตัวตรวจนี้ให้ผล** — ถ้าเอาแถวที่ระบบเพิ่งบอกว่าผิดปกติ
กลับเข้าไปเป็น “ของปกติ” ช่วงปกติจะค่อย ๆ กว้างขึ้นทุกครั้งจนสุดท้ายไม่มีอะไรผิดปกติอีกเลย
และถ้ากลีบปกติยังน้อยกว่า `min_samples` (12) ระบบจะไม่ตัดสินเลย กลับไปเก็บข้อมูลอย่างเดียว

## สองเว็บ สองฐานข้อมูล

| | เว็บ AI สาธารณะ | หน้าเจ้าหน้าที่ |
|---|---|---|
| ที่อยู่ | `web-static/` บน Vercel | `web/templates/` บน Render |
| endpoint | `/public/*` | `/capture`, `/predict-session` |
| ตาราง | `public_scans` | `scans` |
| รหัสตัวอย่าง | เซิร์ฟเวอร์สร้างให้ | ต้องกรอกเอง |
| ผลแล็บ | ไม่มี (ไม่มีคอลัมน์ด้วย) | `compactdry_truth` |
| ชนิดพืช | หอมแดง + กระเทียม (เฉพาะพืชที่มีโมเดลพร้อมตอนนั้น) | ทั้งสองเสมอ แม้ยังไม่มีโมเดล |

ตาราง `scans` เป็นชุดเทรนโดยตรง (`src/export_features_from_db.py` อ่านจากตารางนี้)
ถ้าเว็บสาธารณะเขียนลงตารางเดียวกัน ทุกครั้งที่มีคนกดลองเล่นจะมีแถวขยะปนเข้าชุดข้อมูลวิจัย

เว็บสาธารณะ **คัดกรองอย่างเดียว ไม่เก็บข้อมูลไว้เทรน** รายการพืชที่ให้เลือกจึงคิดใหม่
ทุกครั้งที่โหลดหน้า (`/capture/status?dataset=public`) และตัดพืชที่ตอนนั้นยังไม่มีโมเดลออก
— กระเทียมจะหายไปเองถ้าค่าอ้างอิงใช้ไม่ได้ แทนที่จะรับภาพไว้เฉย ๆ
ส่วนหน้าเจ้าหน้าที่ยังเลือกได้ทุกพืช เพราะการเก็บภาพไว้เทรนคือหน้าที่ของฝั่งนั้น

กระเทียมในเว็บสาธารณะต้องรัน `supabase/migrations/002_add_crop_public_scans.sql` ก่อน
ถ้ายังไม่รัน ตัวเลือกจะไม่ขึ้น (เว็บทำงานปกติ มีแต่หอมแดง) เพราะแถวที่บอกไม่ได้ว่าเป็นพืชอะไร
จะแยกจากหอมแดงไม่ออกตลอดไป — ชนิดพืชเป็นสิ่งเดียวในแถวที่คำนวณย้อนหลังไม่ได้

**นี่คือการแยกข้อมูล ไม่ใช่แยกสิทธิ์** — ทั้งสองตารางเขียนผ่าน service_role เดียวกัน
คนที่รู้ URL ฝั่งวิจัยยังยิงเข้าไปได้ ถ้าต้องกันจริงต้องเพิ่มระบบล็อกอิน ซึ่งยังไม่ได้ทำ

## ระบบเตือนเมื่อผลเชื่อไม่ได้

ออกแบบให้บอกตรง ๆ เมื่อผลไม่น่าเชื่อถือ แทนที่จะโชว์ตัวเลขสวย ๆ เฉย ๆ

- **นอกช่วงข้อมูลฝึก** — โมเดลต้นไม้ประมาณค่านอกช่วงที่เคยเห็นไม่ได้
  ค่าที่เกินไปมากจะตกลีฟเดียวกับค่าสูงสุดที่เคยเจอ แล้วความน่าจะเป็นจะหยุดตอบสนอง
- **ผลก้ำกึ่ง** — เมื่อความน่าจะเป็นอยู่ระหว่าง 0.5 กับเกณฑ์ตัดสิน
  (ฝั่งกระเทียม: เมื่อคะแนนความต่างเกือบเท่าเกณฑ์พอดี)
- **การจัดกรอบมีปัญหา** — หาหัวหอมไม่เจอ / ชนขอบภาพ / ต้องเติมขอบดำมาก
- **ค่ากล้องไม่คงที่** — เทียบ EXIF และความสว่างพื้นหลังระหว่างมุม

## ขั้นตอนต่อไป

1. **เก็บภาพเพิ่ม** — n=60 คือสาเหตุหลักที่ช่วงความเชื่อมั่นกว้าง
   กลุ่มลบ**ต้องมีตัวยาก** (เปลือกถลอก คราบ ช้ำ) เพราะขอบเปลือกฉีกเรืองแสงได้
2. **ทำจิ๊กยึดมือถือ** — วัดแล้วว่าความเข้มแสงเป็นสัญญาณจริง ไม่ใช่สัญญาณรบกวน
   (ตัดฟีเจอร์ความสว่างออกแล้วผลไม่ดีขึ้น) จึงคุ้มกว่าการไปดัดแปลงสูตรฟีเจอร์
3. **ถ่าย S045 ใหม่** — auto-framing พลาด ฟีเจอร์คำนวณจากกรอบกลางภาพ ไม่ใช่หัวหอมจริง
4. ป้ายกำกับต้องมาจาก **CompactDry YM เท่านั้น** ไม่ใช่จากที่ตาเห็นว่าเรืองแสง

## ข้อจำกัดที่ยังค้าง

- สูตร NDFI เป็นนิยามที่เขียนขึ้นเอง ยังไม่ได้เทียบกับเล่มรายงาน
  (ถูกคัดออกจากชุด 10 ฟีเจอร์แล้ว เพราะวัดได้ว่า importance ต่ำกว่ามัธยฐาน)
- ยังไม่ได้ทำ dark-frame subtraction
- ตัวตรวจกระเทียมยังไม่มีผลแล็บมายืนยันสักกลีบ จึงยังวัด sensitivity/specificity ไม่ได้
  รู้แค่ว่ากลีบปกติกี่ตัวที่ถูกแจ้งผิด (`train_flagged` ในไฟล์ค่าอ้างอิง)
- iPhone/HEIC ยังไม่รองรับ (ต้องตั้งมือถือให้บันทึกเป็น JPEG หรือติดตั้ง pillow-heif)
- เกณฑ์ accuracy/recall/kappa ใน `config.json` ตั้งไว้ตั้งแต่เฟส 3
  ยังไม่ได้ตรวจสอบว่าตรงกับที่เล่มรายงานระบุไว้จริง
